# 多路实时监测代码速读记录（2026-09-08）

阅读依据：[多路实时监测实施记录](多路实时监测实施记录_20260905.md)及当前工作区源码（含未提交改动）。本文按调用关系整理，适合先用 5 分钟建立整体认识，再按表定位代码。

**核心思路：每路独立解码、独立维护跟踪状态，共享高低模型和公平推理调度；实时源在积压时优先处理新帧，通过低频检测和帧间光流减少模型调用。**

## 1. 先看整体关系

```mermaid
flowchart TD
    A[main：加载配置和高低模型] --> B[ApiGateway：创建共享组件、注册路由]
    B --> C[POST /streams]
    C --> D[RealtimeStreamManager.create]
    D --> E[每路 decodeLoop：解码线程]
    E --> F[每路有界图像队列]
    F --> G[每路 processLoop：处理线程]
    G --> H[StreamProcessor：准备灰度、光流与轨迹投影]
    H --> I{DetectionCadence：本帧用哪一级}
    I -->|High / Low| J[共享的高 / 低 InferenceScheduler]
    J --> K[YoloEngine：对应模型的 OpenVINO 请求池]
    K -->|future.get 返回| L[StreamProcessor.applyDetections]
    I -->|无需检测| M[StreamProcessor.applyFlow]
    L --> N[finishFrame：提交灰度]
    M --> N
    N --> O[publish：检查帧龄、更新计数、通知订阅者]
    O --> P[SSE 事件 / 状态 API / 指标]
```

模型和调度器按高、低两级共享，每路各有一个解码线程和一个处理线程。`StreamProcessor` 在该路处理线程内创建，保存自己的 tracker、上一帧灰度和可见轨迹；它本身不加载模型、不解码、不创建线程。

## 3. 跟着一帧读 processLoop

1. **取帧。** `takeNextFrame` 对实时源取队尾最新帧并清掉其余积压帧；对本地文件取队首，保留 FIFO 顺序。
2. **检查年龄。** `discardExpiredFrame` 根据本地解码完成时刻判断实时帧是否太旧。这里使用单调时钟 `captured_at`，与供检测节奏使用的 `timestamp_ms` 分开。
3. **准备状态。** `prepareFrame` 生成当前灰度、光流质量及需要的运动投影，只读取既有处理器状态。准备后再次检查年龄，过旧可以直接丢弃。
4. **选择模型。** `DetectionCadence::select` 返回 `High / Low / None`。首帧用高模；高低模型各有独立到期时钟，同时到期先高模，低模保留到期状态。严重光流质量下降等情况可请求紧急高模刷新。
5. **执行检测。** `runModel` 预处理图像，构造 `InferenceContext{stream_id, frame_index, timestamp_ms}`，向对应调度器提交任务并调用 `.get()` 等待。`YoloEngine::infer` 将上下文带回 `InferResult`，结果经本次任务的 future 返回调用方。
6. **更新跟踪。** 成功且未过龄时调用 `applyDetections`；无需检测时调用 `applyFlow`。调度返回 `Stale / Replaced` 计为跳过推理，帧仍新鲜时允许走光流；推理错误单独计数，连续错误达到阈值后该流进入 `failed`。
7. **提交灰度。** `finishFrame` 保存当前灰度，供下一帧光流使用。注意 `applyDetections / applyFlow` 已经更新了轨迹，`finishFrame` 不是统一提交全部状态的事务。
8. **发布输出。** `publish` 再次检查停止条件和帧龄，然后更新处理/检测计数并通知订阅者。如果直到此处才过龄，丢弃对外输出，已经更新的轨迹与灰度仍保留一致状态。

跟踪分工：单模型走 `ByteTracker`；双模型走 `AuthorityTracker`。高模负责稳定轨迹的权威类别、分数及存在性，低模主要修正几何并形成待确认候选，光流在检测间隔传播已有轨迹且受年龄规则限制。不同流可以都有 `track_id = 1`，使用时要结合流 ID。

## 4. 理解多路并发的几个关键点

| 机制 | 当前代码行为 | 为什么要这样做 |
| --- | --- | --- |
| 图像队列 | `StreamContext.frames` 存已解码图像；实时满队列丢最旧帧，处理端再合并到最新帧；本地文件满队列等待空位 | 实时优先新鲜度，文件正常处理时保留完整帧序列 |
| 推理队列 | `InferenceScheduler.queues_` 按 `stream_id` 存待执行张量；满时替换最旧等待任务，返回 `Replaced` | 限制单流待推理积压；这与图像队列是两层不同的缓冲 |
| 单流顺序 | 每个调度器用 `in_flight_streams_` 限制同一流只执行一个任务 | 同一模型级别内避免同流任务同时执行；实时入口自身逐帧等待，也不会并行发出同一路高低模请求 |
| 跨流公平 | ready 队列存流 ID，完成任务后重新排队；有普通任务等待时，紧急任务最多连续取 3 次 | 避免某一路长期独占；公平指选取顺序，不保证各路耗时或 FPS 相等 |
| 实际模型并发 | 网关以 `engine->maxConcurrency()` 设置调度 worker 数；OpenVINO 每个 worker 借用一个请求，`RequestIndexGuard` 在异常路径也归还 | 将调度并发数与请求池容量对齐 |
| 两种过期限制 | `max_request_age_ms` 限制提交后、执行前的等待年龄；`max_result_age_ms` 限制实时帧本地解码至结果提交的年龄 | 排队过旧可省掉推理；已经执行完成但过旧的结果也不发布。后者对本地文件不生效 |

**实时入口目前同步等待推理，没有离线异步 replay。** [config.multistream.yaml](../../yolo_onnx_cpp/config.multistream.yaml) 中虽有 `video_model_async: true`，实时 `processLoop` 并不读取该开关。多路并发来自各路线程与共享调度 worker，不代表单路持续异步提交多帧。

该模板的关键起点是：`max_streams: 4`、队列深度 `2`、两种年龄门槛 `300 ms`、低模节奏 `video_detect_fps: 4.0`、高模节奏 `video_high_detect_fps: 1.0`。模型使用 `throughput`，高低请求数为 `0` 时最终由 OpenVINO 选择。它们是配置目标，不是实测吞吐；输出帧还包括光流帧。

## 5. 接口、生命周期与观测

| 操作 | 代码路径与阅读提示 |
| --- | --- |
| `POST /streams` | 请求体包含 `stream_id`、`source`；调用 `create` 创建线程，成功返回 201。视频源由解码线程随后打开，所以 201 不证明摄像头已经连通；查单流状态确认。重复 ID 或容量满返回 409。 |
| `GET /streams`、`GET /streams/{id}` | 查看状态和计数。网络源断开进入 `reconnecting`，本地文件读完并处理完进入 `completed`；到期为 `expired`，失败为 `failed`。 |
| `DELETE /streams/{id}` | `stop → stopContext`：设置停止标记、清队列、唤醒并 join 线程，再移除记录。自然完成/失败的记录仍占注册容量，需要 DELETE 释放。 |
| `GET /streams/{id}/events` | `subscribe → publish → streamEventToJson`；普通事件名为 `detection`，终止为 `end`。光流帧也用 `detection` 事件名，应结合 `detection_frame` 和 `model_tier` 区分。 |
| `/health`、`/ready`、`/metrics` | 前两者免鉴权和限流；`ready` 只检查流管理器存在。`metrics` 汇总流、调度器、上传任务池和请求门禁统计。门禁入口见 `ApiGateway::registerRequestGate`。 |

SSE 当前只发送订阅后的新事件，256 条内部缓存尚未用于 `Last-Event-ID` 重放。`streamEventToJson` 的数据体没有 `stream_id`，客户端从订阅 URL 关联流；这与内部 `InferenceContext` 带流 ID 的机制要分开理解。

看指标时记住三点：

- `latest_result_age_ms` 是查询时刻减去最近已输出帧的本地解码完成时刻，停帧后继续增大；SSE 的 `result_age_ms` 是该帧发布时的固定延迟。两者均不含相机、网络及解码器内部缓存，首次结果前的状态值 0 是占位值。
- `dropped_frame_count` 只合计解码队列丢帧、处理端合并丢帧、过龄源帧丢弃；`skipped_inference_count` 和 `inference_error_count` 分开统计。
- active 排除终态，registered 反映仍占容量的记录。移除流时，其计数归入 `retired_counters_`，管理器生命周期内的累计量不会随 DELETE 减少。

已有上传视频走另一条入口：`VideoInferenceHandler → VideoJobExecutor → inferVideoFile / inferVideoFileHighLow`。独立有界任务池让整段视频推理离开 Drogon I/O 线程，等待队列满时返回 503；这些视频入口复用同一组高低调度器，也复用 `StreamProcessor`，但检测节奏、异步结果处理和 replay 仍由各入口控制。
