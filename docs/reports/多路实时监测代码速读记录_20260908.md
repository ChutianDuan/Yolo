# 多路实时监测代码速读

源码核对：2026-10-11；文件名保留首次编写日期。本文用于定位源码；算法细节、指标口径和证据边界统一见[综合报告](系统实现与验证综合报告.md)，逐接口调用见[完整流程](初始化到多IP任务提交完整流程.md)。历史构建及实验记录见[报告导航](README.md)。

**每路独立解码、独立维护跟踪状态，共享高低模型和公平调度器；实时积压时处理新帧，通过低频检测与帧间光流减少模型调用。**

## 1. 整体关系

```mermaid
flowchart TD
    A[main 加载配置和模型] --> B[ApiGateway 组装共享组件]
    B --> C[POST /streams]
    C --> D[RealtimeStreamManager 注册本路上下文]
    D --> E[decodeLoop 解码线程]
    E --> F[本路有界图像队列]
    F --> G[processLoop 处理线程]
    G --> H{实时源、异步开关、调度器可用?}
    H -->|是| I[收取旧结果、校验、历史回放]
    I --> J[准备当前帧、更新或提交检测]
    J --> K[共享高低调度器和请求池]
    K -.->|future 在后续帧收取| I
    J --> L[当前帧光流与提交参考灰度]
    H -->|否| M[同步回退：检测到期等待模型，否则光流]
    L --> N[发布前检查停止与帧龄]
    M --> N
    N --> O[SSE、状态与指标]
```

`StreamProcessor` 在本路处理线程内创建，保存 tracker、上一帧灰度和轨迹；不加载模型、不解码、不创建线程。实时与上传视频入口共享调度器，各自管理节奏、回放和输出。

## 3. 跟着一帧读

1. 选择异步或同步回退；本地文件不进入实时异步分支。
2. 取帧：实时合并到最新，文件 FIFO；实时按本地解码完成时间检查年龄。
3. 异步收取已完成 future，核对流、源帧、时间戳、历史与年龄，回放后再次检查。
4. `prepareFrame` 生成候选灰度和运动信息，质量下降可请求紧急高模刷新。
5. 按节奏更新等待票据或提交检测；已执行任务不可替换，高低各有一个 pending 槽位。
6. 异步用校正后的状态传播当前帧；同步在检测到期时等待结果，否则光流。
7. `finishFrame` 提交参考灰度，`publish` 检查停止与年龄并更新计数。
8. 结束时取消等待票据、发布终态；不强制中断执行中的模型调用。

顶层 SSE 帧号表示当前输出，`inference_updates` 表示本次接受的旧检测来源；一条事件可以接受高低两次更新。不同流的轨迹 ID 可重复，应与流 ID 一起使用。

## 4. 容易读错的边界

| 问题 | 结论与详细说明 |
| --- | --- |
| 同帧检测和光流是否算两帧？ | 不重复推进；ByteTracker 的接受帧 tick 与 AuthorityTracker 的源索引年龄不同，见[跟踪时钟](系统实现与验证综合报告.md#tracking-clock)。 |
| 哪个队列丢了任务？ | 解码队列、推理队列、回放历史与 SSE 缓存分别处理，见[资源调度](系统实现与验证综合报告.md#scheduling)。 |
| 模型完成是否等于检测输出？ | 还需要上下文、年龄、回放与发布检查，见[结果核算](系统实现与验证综合报告.md#replay)。 |
| `detection` 事件是否代表模型调用？ | 光流也用此事件名，需读 `detection_frame / model_tier / inference_updates`。 |
| 201 或 ready 是否证明视频源可用？ | 201 仅注册完成，ready 仅检查管理器存在；还要看流状态与计数。 |
| SSE 断线是否停止流？ | 不停止；终态记录仍占容量，DELETE 收尾后释放，见[生命周期](初始化到多IP任务提交完整流程.md#lifecycle)。 |
| 目标 4/1 FPS 是否已达到？ | 是低/高模型预算，不是实测；光流输出率另算，见[测量口径](系统实现与验证综合报告.md#measurement)。 |

模板 `config.multistream.yaml` 的起点是容量 4、队列深度 2、年龄门槛 300 ms、低/高预算 4/1 FPS。这些是配置值，容量结论需查看[对应历史证据](系统实现与验证综合报告.md#evidence)。
